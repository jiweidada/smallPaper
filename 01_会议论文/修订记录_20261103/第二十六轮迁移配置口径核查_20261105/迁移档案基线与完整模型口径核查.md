# 迁移档案中基线与完整模型的评价口径

核查对象为旧稿材料中的 `DEIM_migrated.zip`（SHA-256：`4706b4e4d7032e5264e981c9d59fc9771807cb8a72c5d814363d8054ab29216e`）。对其中 n、s 两个规格的普通基线与 EnhancedStem 完整模型入口，按档案自身的 include 顺序递归解析配置；另以独立字段溯源程序核对覆盖顺序及评价器默认值。这里没有导入项目代码或运行模型。

| 配置字段 | 基线 n/s 入口 | 完整模型 n/s 入口 |
| --- | --- | --- |
| 数据配置 | 档案内 `configs/test/visdrone2019.yml` | 档案内 `configs/test/visdrone2019_mpsma.yml` |
| 配置的评价标注 | `VisDrone2019-DET-test-dev/annotations/test.json` | `VisDrone2019-DET-val/annotations/val.json` |
| `evaluator.using_tiny_metrice` | 显式为 `true` | 未设置；所查评价器构造函数默认 `false` |
| `evaluator.max_dets` | 显式为 `300` | 未设置；所查评价器构造函数默认 `100` |

以上是静态解析结果：默认值的判断以档案内所查的评价器构造和工厂路径为准，并假定命令行或运行时没有进一步覆盖。`max_dets` 指此处的评价器配置，不能直接等同于模型后处理的 top-300 设置，也不能据此推断 VisDrone 官方挑战赛的评价规则。直接使用这四个入口而不统一配置，不能形成评价条件匹配的比较。

**证据边界：**档案没有将这些入口及其最终参数与所讨论的历史指标、具体运行或数据文件内容绑定。本核查不能证明历史表格实际混用了验证集和 test-dev，也不能计算两种评价口径导致的指标差异。会议修订稿现已将本地验证集结果和外部 test-dev 结果分开描述，因此此轮不根据假设改写正文。

上一轮比较了完整模型 n/s 入口在两份代码树中所引用的特定数据配置：档案内的 `visdrone2019_mpsma.yml` 与现存代码树中其对应的 `visdrone2019.yml` 字节一致。那不是说**迁移档案内部**的通用 `visdrone2019.yml` 与 `visdrone2019_mpsma.yml` 一致；本轮比较的正是档案内这两个不同的配置文件。

同目录旧迁移清单、迁移脚本和打包脚本记载了把部分现存自定义模块和配置复制进较新版 DEIM 后打包的过程。这解释了两份改进方法源码相同但训练器存在差异的可能来源；这些记录本身不认证实际历史训练所用源码，也不构成独立复现。

材料：

- `archived_config_resolution.json`：四个入口的包含链、最终字段、源文件哈希及无执行解析方式。
- `independent_field_provenance.json`：字段最后覆盖位置、评价器默认值及工厂路径的独立核对。
- `source_snapshot/` 和 `migration_records/`：本轮所查配置、代码及迁移记录的留存副本。
- 上一轮的 `迁移档案与现存源码比对说明.md`：源码身份与训练器差异的已有证据边界。
