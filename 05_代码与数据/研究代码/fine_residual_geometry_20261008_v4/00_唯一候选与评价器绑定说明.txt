fine_residual 唯一候选：v4 完整评价器绑定与原生接口核验

结论
唯一主候选仍为 fine_residual，baseline 与 fused_residual 仍为必要对照，两 seed、132 轮原协议不变。geometry.py、residual.py、stage_trace.py 和六份模型配置与 v3 逐字节相同。没有新增主干、损失或第二个改进方案。
本版解决的是评价身份缺口，并验证了正式训练源码的导入、六份配置读取和三个新初始化模型的 CPU 接口。未训练、未加载共同初始化/训练 checkpoint、无新 AP，不证明该方案最有效或创新成立。

为什么需要本版
v3 只保存 cocoeval.py 的 SHA。但原 COCOeval.computeIoU 实际通过 mask.iou 调用 _mask 编译扩展；即使 cocoeval.py 相同，扩展不同仍可能改变 IoU 和评价结果。用户提供的源码中，编译分支还受原文件夹名影响，进一步说明只核对一份 Python 文件不充分。

已落实到代码的改变
prepare 要求 --evaluator-root 指向实际 pycocoeval 包目录，将六份已验证 Python 源码与一个编译扩展的 SHA 一起写入准备身份。
verify_bundle 在训练前核对所有文件；训练入口在导入 engine 前激活该目录，检查实际加载的七个模块，以及 cocoeval.maskUtils、mask.iou 到扩展的引用关系。
运行开始回执保存完整评价器身份；最终结果 capture 再次核对实际模块。六次正式结果比较要求源码和编译扩展均一致，并与各自准备身份一致；旧的只含 cocoeval.py SHA 的记录不会被当作本版结果接受。
这种绑定证明文件与调用来源一致，不单独证明编译扩展算法正确，也不证明与历史远端二进制数值等价。既有历史复现超差仍保留。

准备包与入口
本版 prepared_local 下已有三组、两 seed，共六份 PREPARED_NOT_TRAINED 准备包；runs 不存在。
本地 evaluator_root 已指向前一轮建立的 Windows CPython 3.10 独立评价目录，启动时由 experiment.py 显式加入搜索路径，不依赖全局安装。
native_import_deps 是额外的本地导入依赖目录，工程脚本显式使用它。直接执行 train 时也需要在该子进程的 PYTHONPATH 加入此目录，或使用已经具有对应依赖的完整环境；不要把工程脚本的导入成功当成默认解释器已全局安装这些包。

可重跑的只导入及配置核验（不训练，输出必须为新路径）：
python check_native_import.py --bundle prepared_local/baseline_seed1 --extra-python-path native_import_deps --read-configs --output <新回执路径>

未来经授权训练仍使用：
python experiment.py train --bundle prepared_local/<arm>_seed<seed>
需要完整原生运行环境，并按上一段在子进程设置本地补充依赖路径；本轮没有执行此命令。
迁移到 Linux 时不能使用本地 .pyd；必须使用目标环境实际安装的 pycocoeval 包，重新 prepare 并绑定其 .so。三组两 seed 必须用相同的完整评价包。路径或环境改变不能手改旧回执。
结果比较使用本版 results.py，要求六份实际完成训练的 endpoint、last.pth 和阶段归档；工程数据和旧版输出不能替代新实验。
