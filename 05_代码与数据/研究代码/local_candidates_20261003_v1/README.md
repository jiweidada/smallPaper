# 两条候选的本机实现说明

状态：2026-10-03本机代码准备。两条路线分别实现，不与C组合，不替换当前C4或C8/O8作业。原始验收目标继续沿项目既有入口推进。这里是代码使用与设计说明，不是另一份“当前实验计划”。

## 设计判断与依据

**建议优先验证局部与全局对齐融合。** 它直接检验“局部目标像素增加以后，全局特征能否提供额外有用信息”。640整图与裁块分别检测后合并是必须保留的对照；增加输入和窗口本身不能证明交互贡献。现有尺度诊断支持提出这个假设，但目前无法证实本实现提高APs，也尚未完成它的近邻新颖性核对。

**查询覆盖保留为较低优先级。** 原生DFINE代码在解码器前按最大类别分数取300个位置。没有候选阶段证据证明该步骤是主要瓶颈。因此先提供能导出的诊断和可关闭的选择器，不直接提高查询数量，也不叠加新的分类、定位或注意力模块。

本实现的本机基底是HGNetv2-B0、HybridEncoder和三层DFINE。`native_source_manifest.json`记录31个来源文件，其中模型、损失、匹配、注意力和查询路线数据增强的叶文件均按原始字节复制；仅包导入入口改为精简显式导入。共享源码保持原位。`native_recipe.yml`保留完整来源配方，但训练数据路径由命令行提供，不会使用其中远端路径启动旧作业。

## 第一条：全局与裁块对齐，只交互局部P3

主要文件：`dataset.py`、`geometry.py`、`dual_view.py`、`evaluate.py`。

1. 同一原图产生整图缩放640和原图裁块640。窗口640、步幅512、末端贴边；图像不足640时在右下补黑，不把原生裁块放大。训练每张原图均匀选一个窗口，不用GT选窗口；验证覆盖全部确定窗口。
2. 两路共享一个骨干。训练将两路图像拼成2B，在同一次骨干调用中取得特征，保证两臂的共享BN处理方式一致。
3. 根据裁块的原图归一化xyxy坐标，为局部P3各位置生成对应全局P3采样网格。使用`grid_sample`的`align_corners=False`约定，并屏蔽落在补边区域的上下文。
4. `concat(局部P3, 对齐全局P3) → 1×1压缩至64 → SiLU → 深度3×3 → SiLU → 零初始化1×1恢复至256 → 局部P3残差相加`。不直接改局部骨干P4/P5，之后仍交给原编码器和解码器；编码器后各尺度受融合影响是该路径的总效应。
5. 全局、局部均受原生检测损失监督，按0.5/0.5汇总。空裁块允许没有原生去噪损失项，不补造目标或去噪项。训练时全局上下文可接收局部损失梯度；零初始化时融合输出严格等于独立两路。
6. 验证每原图只计算一次全局特征/预测，并缓存给所有裁块；局部预测映射回原图。两臂都做类别内NMS=0.5，原图最终top300，COCO maxDets=[1,10,100]。保存合并前的全局和每个裁块预测，避免只留下最终指标。

| 配置 | 检验内容 | 参数/输入关系 |
|---|---|---|
| `configs/dual_independent.yml` | 同样两路分别检测后合并 | 融合模块存在于共同初始化中，但冻结且不执行 |
| `configs/dual_aligned.yml` | 对齐全局P3是否增加局部有效信息 | 执行上述局部P3交互；相对独立臂新增49,728个活跃参数 |
| `configs/dual_local_residual.yml` | 同参数局部残差是否解释收益 | 同一模块只接收局部P3；这是准备好的辅助配置，未自动安排第三条训练 |

关键限制：全局P3的感受野可以含裁块外信息，但这不是对整幅场景语义的全覆盖保证；当前没有额外P5池化或全局注意力。裁块相交且宽高≥1像素的GT裁剪后作为局部监督，最终评价仍使用原始完整GT。截断目标、裁块暴露量、重复框和场景覆盖均需在真实实验中记录。

为了保留可解释的一张原图到两张视图的坐标关系，双路配方使用共同翻转和亮度变换，暂不使用Mosaic、ZoomOut、IoUCrop或MixUp；最后12轮关闭亮度变换，仍保留翻转。**双路两臂彼此采用同一新配方，但这不是相对旧C4或D1的单变量比较。** 不复用旧正式结果作为这条路线的训练对照。

## 第二条：保持300个查询，检验P3空间覆盖

主要文件：`query_coverage.py`、`diagnose_queries.py`。

实现通过继承原生`DFINETransformer`，仅替换`_select_topk`，继承原编码器预测头、解码器、去噪和损失：

- `reserve=0`严格调用相同的原生topk逻辑，包含相同的分数相等处理；与原方法得到相同索引和gather结果。
- `reserve=75`先保留分数最高的225个有效位置；剩下至多75个位置从最小锚框尺度组的4×4空间网格中逐轮选出，每轮每格至多一个，格内按分数排序。
- 候选最大logit必须不低于本图最佳logit减2，避免强制填入极弱网格响应；不足的名额从其余全局高分有效位置补齐。
- 保持300个唯一位置，不改变分数、300匹配查询、100去噪配置、后处理或评价上限。训练和推理使用同一选择方式，选择索引无梯度，选中的特征和原预测头仍接受梯度。

**这里P3是“最小锚框尺度组”的代理，不是已预测或已确认的小目标。** 选择时不读取GT，不额外计算全部位置的回归头。网格/名额/logit差值均为首版固定假设，未在验证集调优。没有新增参数，但Python分组与选择可能增加时延，不能据参数为零声称成本为零。

开启`evaluate.py --trace`会额外计算全部8400个位置的预解码框，导出原始logits、框、锚点、有效标记和300选择索引。这些额外计算只用于诊断，不用于选择，也不计入正常推理时延。`diagnose_queries.py`分块比较全部有效候选与被选候选的同类IoU=.50/.75覆盖，并区分原始COCO-small GT。该结果是**预解码候选覆盖代理，不是APs、最终召回率或因果结论**。

两个查询配置只改变reserve=0/75；它们的数据增强和collate复制原生配方，包括原定Mosaic、ZoomOut、IoUCrop、MixUp日程。运行驱动、EMA/选权及评价也需两臂共同采用，不能直接替代旧冻结baseline。

## 本机验证完成了什么

`cpu_verification_v1.json`有45项检查，`cpu_integration_v4.json`有14项接口检查：共59项通过。包括原生B0/编码器/三层DFINE在640输入下的前向与反向、零融合等价、局部P3唯一直接变化、全局特征梯度、空裁块、坐标对齐与补边、NMS回映射、300查询唯一性及默认等价、共享初始化加载、真实CPU optimizer更新、缓存一致性、完整COCO导出和无干预候选诊断。

模型前向/反向使用合成数据、CPU的1个原图对；查询数据加载器另外验证了真实batch8张量。**这不是GPU batch8容量验收，也不是VisDrone上的训练或性能结果。** 首次发现的空裁块损失键差异已修复；早期CPU评价环境为pycocotools2.0.10，最后接口验证已切换到项目官方版本2.0.11。历史回执保留，当前以v4为准。本机Torch2.7.0与实际远端2.5.1存在版本差异，远端算子/数值兼容仍须实测。

实际参数计数见`parameter_counts_actual_v2.json`，交付源码哈希和边界见`local_delivery_manifest_v2.json`。

## 使用入口与后续验收

本机CPU验证可在本目录运行，输出文件必须用未存在的新名字：

```powershell
& 'C:\Users\jiwei\.conda\envs\py310\python.exe' verify_cpu.py --output cpu_verification_new.json
& 'C:\Users\jiwei\.conda\envs\py310\python.exe' verify_integration_cpu.py --output cpu_integration_new.json
```

GPU准备入口是`run_candidate.py capacity`，正式训练入口是`run_candidate.py train`；二者必须显式提供配置、公共初始化及SHA、真实训练数据、输出目录和实际GPU UUID。`train`还需要本臂已通过且源码/配置/初始化/数据/设备绑定一致的容量回执，以及完整val路径。没有自动控制器、重试、续训、缩小batch或改变配方行为；不会停止已有作业。

容量入口预设batch8，对0/4/7/46/84阶段分别做2批普通与3批真实高密度样本，共25批。需全部真实optimizer更新成功、自然分配峰值≥10 GiB且保留显存余量；不靠填充显存通过。失败保留，不自动把batch改回16。**现有C8/O8的18.26 GiB测量不能复用来证明双路容量**；双路batch8是8个原图对、16张640输入视图，需重新实测，可能因两路反向图出现OOM。

6471训练图按batch8/drop_last，每臂808批/轮、96轮77,568计划更新、6464原图/轮，末尾7图丢弃。双路每臂共620,544个原图对暴露、1,241,088张视图；若548图窗口数仍为既有规则的2842，则每次val为3390张视图。本准备驱动每轮全val选最高总体AP EMA，再做选中EMA独立val，因此评价预算也明显增加。以上为计划次数计算，不是实测时间。

这套驱动是可运行的研究准备入口；还没有执行完整96轮，也没有完成新实验的生产锁、所有目标暴露审计、第二评价器一致性及完整归档验收。`review_pair.py`只给预审，不能输出原C正式验收通过。

后续唯一优先方法验证仍是双路**独立合并 vs 对齐融合**的匹配比较。保持窗口、数据、公共初始化、seed1、训练batch8、96轮、优化步数、损失权重、选权和原图评价一致。方向条件使用候选减对照APs>0、AP/AP75≥0、至少两项严格正，同时披露全部12项、逐类APs和实际代价。数字近零或由极少样本类主导时，不用简单通过方向条件宣称稳定有效。

若融合没有优于同预算独立合并，降低该交互结构优先级；若同参数局部残差表现相当，不能把收益归因于全局信息。查询路线只有在同权重的候选诊断显示确实存在选择阶段损失、且固定75名额改善相应覆盖时，才考虑匹配训练；否则停留为诊断，不靠增加查询数挽救假设。技术OOM/接口失败与完整有效实验的性能负结果分别记录。


复制到Linux时排除`local_deps`和`__pycache__`，使用目标运行时自己的依赖；本地依赖中有Windows编译包。源码路径已规范为可移植相对路径，GPU入口不会加载Windows依赖。
