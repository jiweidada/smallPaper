## 一、336 阶段1 哪些"通过"不成立，为什么

| 336 报告 | 337 结论 | 原因 |
|---|---|---|
| "U_W 闭合 32/32 通过" | **不成立** | G_W/U_W 恒为 0，是 `0 == 0 & ...` 的空洞成立 |
| "窗选择 vs 手算 32/32 一致" | **不成立** | 手算用的是同一批错误中心，只是自洽性，不是正确性 |
| "全部通过" | **不成立** | 见上两条 |
| 确定性 / 缓存读写 / 耗时 | **仍有效** | 与坐标无关 |

**根因（主控指出，已复现）**：
- `pred_boxes` 是归一化 cxcywh，被当成 640 像素 xyxy 用。8 个旧缓存文件 xyxy 合法率 0.000（3536 为 0.0067），第 2/3 列最大 0.048–0.343。
- GT 是原图像素（如 1400×788），直接除以 640，未按 640/orig_w、640/orig_h 缩放。
- 结果：G_W、U_W 全 0，而每图有 7–127 个 GT。

**另一处（336 未说明）**：子集不是 336 要求的 development 前 32 个，而是 `[269,5429,3536,…]`。337 已改回前 32 个（`[1,2,3,5,6,7,9,10,12,13,14,16,17,18,19,20,21,24,27,28,29,30,34,35,37,38,40,44,46,47,52,53]`）。

## 二、坐标管线（按 296 L11/L45，有独立单元测试）

- **全局输入**：自然 RGB → PIL Resize(640,640) **拉伸** → float32/255（296 L45）
- **pred_boxes**：归一化 cxcywh → ×640 → xyxy（640 平面）
- **GT**：标注像素 xywh → xyxy → ×(640/orig_w, 640/orig_h) → 640 平面
- **窗**：**64×64 像素的窗**，网格步长 64 px，即 640 平面为 **10×10=100 个候选窗**（依据 262 `make_grid`：`(x,y,min(x+64,w),min(y+64,h))`，`range(0,h,64)`）
  - **更正**：336 里我误按"64×64 个 10px 小格"实现，实际是 64 像素窗口。这一条已在 v2 修正。
- **裁片**：W(640) → 原图像素 ×orig_w/640、×orig_h/640（296 L45 公式）

单元测试（`337_result_coord_unit_tests.json`）：归一化→640、原图→640（1400×788 非方形）、边界整图、窗→原图、往返，**5/5 通过**。

## 六、重大发现（待主控，未自行处理）

**317/296 的选窗规则在 BASE24 raw + VisDrone development 上系统性选到无 GT 区域。**

| 选窗依据 | G_W>0 的图数 | 平均完整 GT 数 |
|---|---|---|
| 按 317 规则（原 final300 预测中心数最多） | **4 / 32** | 0.56 |
