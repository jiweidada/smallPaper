一、val548 上 tiny Geo0 的实测分解（两 seed）
================================================================
A. 主要是宽度的问题，不是高度
- tiny GT 中宽为短边的有 4943/4952，高为短边的只有 9（348b）。GT 宽<4 有 4947，高<4 只有 82（348c）。
- 原因：val 548 张图全部是 16:9（1360×765 有 408 张，960×540 有 121 张，1920×1080 有 19 张）。拉伸到 640×640 后 x 轴缩放比是 y 轴的 0.562 倍（348e、标注统计）。tiny 的 640 宽高比中位数：val 0.241，train 0.321。
- train 里 3302/6471 张是 4:3（sx/sy=0.75），其余是 0.56，所以训练集和验证集的形变程度不同（train.json 统计）。
- 纯标注算术（348e，不涉及模型）：
    输入形状              短边<4 的 GT 数   像素数
    640×640 拉伸          5096              409600
    800×512               2531              409600
    853×480（16:9）       2669              409440
    960×540               1430              518400
  像素数相同、只换成接近原图的宽高比，按 640 口径定义的 tiny 数量就减少约一半。这是定义层面的算术结果，不代表检测会变好。

B. 附近有候选，但它们太宽，x 方向也偏
- Geo0 tiny 的 maxIoU 分布（348a）：IoU=0 的 334/345，(0,.1) 的 802/918，[.1,.5) 的 2579/2464。也就是说，多数 GT 已有候选与之部分重叠。
- 中心最近的候选，其中心落在 1 个 GT 尺寸以内的：2643/2571。有任一候选中心落在 GT 框内的：1686/1589。
- 中心最近的候选，宽度比 >1.5 的：3099/3211；高度比 >1.5 的：1083/1245（348c）。
- 轴向 oracle（348c）：把最近候选的 x 区间换成 GT 的 x 区间（y 不动），IoU≥.5 的有 2548/2470；换 y 区间的只有 830/744；只修中心、不修尺寸的只有 624/584。
  只缩宽度、中心不动（宽高截到 ≤1.5 倍 GT）时只有 378/352（348b）。所以 x 方向的中心和宽度都要修，单修一个不够。
- 最近候选已被另一 GT 以 IoU≥.5 占用的：790/758。未被占用且 x 修正后 IoU≥.5 的：2031/1991（348e）。

C. 预测宽度有一个大约 3–4 px 的下限（640 坐标，348d）
- final300 预测宽度 <4 的只占 3145/164400（seed1）、2192/164400（seed2）；宽度的 10% 分位数是 5.75/6.36。
- 按 GT 宽度分段，看 maxIoU 最大的那个候选的宽度中位数：
    GT 宽 [0,2)：7.37/8.14，其中 IoU≥.5 的只有 17/13（共 536 个）
    GT 宽 [2,3)：5.25/5.50，IoU≥.5 的 367/367（共 1894 个）
    GT 宽 [3,4)：5.55/5.73，IoU≥.5 的 853/845（共 2517 个）
  已匹配上（IoU≥.5）的 GT 宽 [2,3) 段，预测宽度中位数为 3.67/3.59，已经接近一维 IoU 的极限：GT 宽 2、预测宽 4 时，即使完全对齐，一维 IoU 也只有 0.5。
- 对照组 small（短边 4–16）：Geo0 为 7024/6984（共 22197）。其中只修中心就能达标的 1397/1529，“中心和尺寸都修不好”的只有 6/26；而 tiny 中这一项是 435/518（348b、348c）。

D. 其它维度（348a，两 seed 接近）
- 按类别（tiny 数→Geo0 数，seed1）：pedestrian 2635→2100，people 983→680，motor 559→322，car 492→407，bicycle 156→117，其余类合计 127→89。
- 按局部密度（中心 32 px 内其它 GT 数）：Geo0 中 6–10 个的 1157，11–20 个的 981，>20 个的 373，0 个的只有 46。tiny 整体的分布与 Geo0 相近，没有看到 Geo0 特别集中在高密度区。
- 集中度：Geo0 最多的 55 张图（10%）占 1779/3715。
- 最近候选的分数：落在 [.1,.3) 的 2590/2528，≥.5 的只有 99/97。

E. 缓存没有的信息
342 val 缓存不含 encoder/decoder 中间层、pre/aux 输出、DN 和 query 层级信息，所以无法按“query 层级 / 编码器层级”分解。这一点没有做。

结论：在 val548 上，tiny 漏检的主要几何形态是附近有候选，但候选在 x 方向偏离而且太宽；同时预测宽度存在约 3–4 px 的下限，而 640 拉伸把这些目标的 x 方向压到了 0.47 倍。276 在 development 图上的“候选回收新增 0”仍然成立，但不能再拿“93% 根本没有候选”来描述 val。

================================================================
二、候选研究主线
================================================================

候选 1｜等像素、保持宽高比的输入（检验“tiny 是 x 压缩的产物”）
1. 瓶颈：一·A 与一·C。tiny 中 99.8% 是因为宽度小；拉伸让 x 缩放只有 y 的 0.562 倍；预测宽度有 3–4 px 下限。等像素换宽高比后，按定义算的 tiny 数从 5096 降到 2531（800×512）或 2669（853×480）。
2. 查新：
   - DETR 默认的预处理就保持宽高比（短边 800、长边不超过 1333）：https://huggingface.co/docs/transformers/v4.43.4/en/model_doc/detr
   - RF-DETR 代码同时提供方形缩放和保持宽高比两种模式：https://github.com/roboflow/rf-detr/blob/develop/src/rfdetr/datasets/coco.py
   - 小球检测为 Full-HD 用 960×544 输入，并指出方形拉伸会让小目标变形：https://pmc.ncbi.nlm.nih.gov/articles/PMC8124271/
   - 一篇 VisDrone 实践博客报告：同尺寸下拉伸优于 letterbox，保持比例的更大输入更好（只有 F1，没有小目标指标）：https://towardsdatascience.com/custom-training-pipeline-for-object-detection-models/
   - 不对称步长：MatrixNets：https://arxiv.org/abs/2001.03194
   - 输入分辨率与 APs：ICCV2025 UGS 中 TPH-YOLOv5 从 640 到 1536，APs 14.1→22.4（方形，没有改宽高比）：https://www.openaccess.thecvf.com/content/ICCV2025/papers/Sun_Uncertainty-Aware_Gradient_Stabilization_for_Small_Object_Detection_ICCV_2025_paper.pdf
   已有覆盖：保持宽高比、提高分辨率都是常规工程，本身不算方法创新。
   没查到：在 DETR 类检测器上做“等像素、只改宽高比”，并按原图尺寸固定 tiny cohort 的对照实验。查不到不等于没有。
   增量：主要是诊断价值。它是所有 tiny 方法都必须先过的简单对照，包括当前主线和候选 2。不建议把它当作论文的主方法。
3. 判据与对照：
   - cohort 用原图像素定义并固定（例如原图短边<8），不随输入形状变化，避免靠改定义“减少 tiny”。
   - 对照臂：640×640 拉伸。实验臂：同像素、保持宽高比，例如 832×480（32 的倍数，399360 像素，为 640² 的 0.975 倍）。train 中 4:3 图要处理一致（pad 或按比例取形状），否则训练/验证形变不一致这一混杂仍在。
   - 事前判据：两 seed 各自的 APs、AP 与固定 cohort 的 Geo0 减少量方向都严格为正才保留；零不算正；mixed 就停。
   - 零训练预检（只描述，不作为判据）：用现有 BASE24 权重直接在 832×480 上推理。由于训练时是拉伸，这里存在分布偏移，结果只能说明现有权重的敏感性。这一步需要模型前向，交给 Codex 做。
   - 失败的解读：如果等像素保持比例对 APs/Geo0 没有改善，说明 x 压缩不是原因，tiny 问题应归到绝对分辨率，即 C 线（P2）和更大输入的方向。
4. 成本：
   - 零训练预检：342_raw_seed1_resumed_result.json 实测 516 次 640 输入 CPU 前向用了 97.43 s，约 0.19 s/图。832×480 像素数相近，按此外推 548 图×2 seed 约 3.5 分钟。
   - 正式检验需要完整重训检测器（不是只训头），必须用 GPU。我读过的本地文件里没有 BASE24 的 GPU 时长，这一项成本未知。
5. 关系：与当前主线互相独立，不替代它；当前主线的结果出来之前就可以先做零训练预检。与 C 部分重叠，因为 P2 也提供更高的横向分辨率，所以 C 加上保持宽高比是否叠加需要单独检验，不能事先假设。

候选 2｜x 轴亚像素定位：拆掉预测宽度的下限
1. 瓶颈：一·B 与一·C。tiny Geo0 中，只修最近候选的 x 区间就能到 IoU≥.5 的有 2548/2470（约 2/3），且其中 2031/1991 个候选未被别的 GT 占用；修 y 只有 830/744。预测宽度 <4 只占 1.3–1.9%。
2. 查新：
   - Sized L1（按 GT 宽/高归一化的 L1，COCO 上 Co-DETR APs 35.4→38.2）：https://arxiv.org/abs/2410.22638
   - NWD（小目标的 Wasserstein 度量，用于标签分配和损失）：https://www.sciencedirect.com/science/article/pii/S0924271622001599
   - HF-D-FINE（Outer-SNWD 损失，含 VisDrone/AI-TOD）：https://www.sciencedirect.com/science/article/pii/S0262885625004226
   - D-FINE 的 FDR 偏移按参考框宽高缩放，小参考框对应的修正范围也小：https://arxiv.org/abs/2410.13842
   - DEIM：https://openaccess.thecvf.com/content/CVPR2025/html/Huang_DEIM_DETR_with_Improved_Matching_for_Fast_Convergence_CVPR_2025_paper.html
   已有覆盖：尺度归一化损失和 NWD 已有直接先例。本地 244 的 FDR 4px floor 方向相反（它是加大最小步长），结果 mixed 已停，不能拿来救这一方向。本地 290 的 ROI 精修已做过“给局部 RGB 让小头修框”，结果阴性；但它冻结了候选身份，位移限制为 0.2×旧框宽高，几何监督只覆盖已绑定的 .5/.75 GT，没有对 Geo0 tiny 给过 x 方向的目标。
   可能剩下的增量：只针对 x 轴、只针对“附近已有未占用候选”的 tiny 做定位，并让监督直接到达这些 GT。前提是能证明问题出在回归表示（宽度下限）而不是分配（这些 GT 本来就没有 query 被分到）。现有缓存分不开这两者，这是本候选最大的未知。
3. 判据与对照：
   - 最强的简单对照依次为：候选 1（只改输入）；Sized L1 或 NWD 的全局替换；290 的 always-refine（已有数字：raw ΔAPs +.016327713pp，degraded +.024486581pp）。
   - 需要先做一项只读诊断（还需要缓存补充字段）：对这些 GT 在训练中是否分到过 query、FDR 宽度一侧的分布是否顶在边界上。如果这些 GT 普遍没有 query 被分到，这一候选退化为分配问题，与当前主线、DEIM 的 dense O2O 重叠，就停。
   - 事前判据：两 seed 各自的 tiny Geo0 正式新增 TP 和 APs 都严格为正，而且胜过 Sized L1 对照；零不算正；mixed 就停。
   - 失败的解读：如果打破宽度下限后 TP 没有增加，说明瓶颈在分类分数或 top-k 预算（一·D：最近候选分数多在 .1–.3），而不在几何。
4. 成本：如果只训小头、缓存前向，参考 348 的实测，1218 步用 579.47–609.91 s，约 0.48–0.50 s/步（N_seed1、S_seed1 的 outcome.json）。要改 FDR 或损失并让整网参与，就必须用 GPU，成本未知。
5. 关系：建议在候选 1 的结果之后做；如果保持宽高比已经消除了大部分宽度下限的影响，候选 2 的作用空间会变小。与当前主线互补：R 臂生成的新框用的是同一套回归表示，如果宽度下限存在，R 新生成的 tiny 框也会受影响。

（没有列第三条。当前主线的补充建议见下面第四节。不再单独提出 query 初始化或密度 query 方向：Dome-DETR PAQI https://arxiv.org/abs/2505.05741 、DQ-DETR、D3Q https://github.com/XianHYe/mmdet3-D3Q 、MR-DETR https://www.sciencedirect.com/science/article/pii/S0167865526000048 都已经覆盖“按密度增加 query”；而本地数据显示 tiny Geo0 附近多数已有候选，增加 query 数不是首要缺口。）

================================================================
三、推荐排序
================================================================
1. 候选 1 的零训练预检优先。不需要训练、成本已测，而且它决定了“tiny”这个问题有多少是 640 拉伸造成的。如果这部分很大，当前主线、C 线以及论文中所有关于 tiny 的论述都要面对这个对照。
2. 候选 2 放在候选 1 之后，并且先补“GT 是否分到过 query、FDR 宽度一侧是否顶边界”的只读诊断再决定。新颖性风险高（Sized L1、NWD 都已存在）。
两条都可能落到“工程修正，没有方法增量”，这一点现在无法排除。
